# SwoftyMod core

The in-game half of Swofty Launcher for F1 25. `native/build.sh` writes it to `native/dist/` in the game folder's layout. The launcher places these files in the game folder for a modded session and removes them when the game exits.

| File | Source | Role |
|---|---|---|
| `version.dll` | `src/loader/version.c` | Proxy for the system `version.dll`. It forwards every export, does nothing in any process other than `F1_25.exe`, and loads every DLL in `swofty/addons/core/`, then `swofty/addons/*.dll`, just before the game creates its window. It also loads `swofty/mods/core/` and `swofty/mods/*.dll` with them, in name order, until the next minor release. |
| `swofty/addons/core/swofty_core.dll` | `src/core/` | SwoftyMod. Adds ADDON SETTINGS directly under CAREER on the home screen, runs the mixin API (version 3) for plugins, bridges ADDON SETTINGS commands to `swofty/settings.json` and the requests file, registers addon screens and drives their view models, reports the special liveries that addons add as owned (`owned_items` in `swofty/settings.json`), and writes crash reports. |
| `swofty/addons/core/swofty_gamelog.dll` | `src/gamelog/` | Copies the engine's own log lines into `loader.log`. |
| `swofty/addons/core/bindings.json` | `re/tools/bindgen.py` | Game functions, data and call sites that plugins can bind to, with their signatures. |
| `swofty/addons/core/symbols.tsv` | `re/tools/bindgen.py` | Function names by address, for crash reports. |
| `swofty/addons/core/log_channels.tsv` | `src/gamelog/log_channels.tsv` | The engine's log channels, for the game log filter. |
| `swofty/addons/core/features.json` | `FEATURES` in `src/core/stage.cpp` | The runtime asset features of this core, each `stable` or `experimental`. |

Everything logs to `<game>/swofty/loader.log`, or to `%LOCALAPPDATA%\Swofty\state\loader-fallback.log` when the game can't create that file. Plugins get the C ABI in `packages/sdk/include/swofty_api.h` and the C++ helpers in `packages/sdk/include/swofty/mixin.hpp`. The generated game headers are in `include/swofty/game/`.

## Core

- **Settings bridge.** Core wraps `FeHome_Handle_Command` and handles the commands that `swofty/settings.json` assigns to each option, each addon's ENABLED switch and APPLY & RESTART. It updates plugin settings live and writes each change to the requests file that the launcher merges into the profile. APPLY & RESTART closes the game window so the launcher can rebuild and relaunch.
- **Crash log.** A vectored exception handler writes the exception, the registers and a stack named from `symbols.tsv` to `loader.log`. Calls to `ExitProcess` and `TerminateProcess` are logged with the caller's stack.
- **Crash reports.** On a fatal-class exception that reaches the top-level filter, the game's own fatal paths (a fatal `Ne_ReportMemoryError` heap error, hooked by its prologue, and `Ne_FatalAbort`), and an `ExitProcess`/`TerminateProcess`/`NtTerminateProcess` with a non-zero code or one that follows a fatal exception, core writes `swofty/crash-<time>.txt` and a minidump beside it, once per process. A dedicated thread writes them while the faulting thread waits, so a stack overflow or a corrupt stack still gets a report. A fault while it writes cuts only the section it hit: the report names the fault there and goes on with the next section. The report holds the stack walk and a return-address scan, all registers, the bytes around `rip` and around every register that points into readable memory with its region, the faulting address's Ne heap block with its neighbours and guard state, the loaded addons and modules, a lock-free ring of recent flow, session and screen events and game-log warnings, the live profiler counters, the thread list and the last 200 `loader.log` lines. `MiniDumpWriteDump` writes the dump with the report as its comment stream, capped by a per-stack budget; `SWOFTY_CRASH_DUMP=full` dumps all memory and `off` skips it. Core keeps the last 8 reports and 3 dumps. A crash whose registers hold a DXGI device-removed HRESULT writes `swofty/dred.flag`, and the next session forces D3D12 DRED on (`SWOFTY_DRED=1` always, `0` never) by setting breadcrumbs, page fault and breadcrumb context enablement before the game's `D3D12CreateDevice`, which core hooks to keep the game's devices. When a kept device reports removal, the report's `GPU device removal (D3D12 DRED)` section holds the removal reason, up to 32 command list nodes (unfinished first) with 64 operations around the last completed one, and the page fault address with up to 32 existing and 32 recently freed allocations.
- **Addon screens.** Core reads the `"ui"` block of `swofty/settings.json` (or `swofty/ui.json`) and registers each listed screen file from `swofty/ui/` through the engine's own screen loader when the screen's flow loads. A route to an addon screen that is not registered is cancelled and the last screen reopens, instead of rebooting the front end. Every node the engine rejects is logged with its reason.
- **View models.** For each screen with `"view_model": true`, core registers a view model under `view_model_data.<screen>`. `swofty_addon_<N>` pages map to `addons[N]` of `swofty/settings.json`: they publish `title` and `o<k>.label`, `o<k>.text`, `o<k>.value`, `o<k>.min`, `o<k>.max` per option, and handle `swofty_next:<addon>:<option>`, `swofty_prev:<addon>:<option>` and `swofty_set:<addon>:<option>:<index>` through the settings bridge.
- **Plugins.** A plugin exports `SwoftyAddonInit` (`SWOFTY_ADDON()` in `mixin.hpp`). The loader also calls `SwoftyModInit` when that is the only export, and `SWOFTY_MOD()` is an alias of `SWOFTY_ADDON()`. Core reads `addons` and `owned_items[].addon` from `swofty/settings.json`, or `mods` and `owned_items[].mod` when the new fields are absent.
- **Mixins.** Plugins wrap functions, call sites and virtual table slots by binding name. Core orders each chain by priority and load order. With a `swofty/session.json`, registrations not declared there are refused.
- **Binding resolution.** Core resolves each binding from `bindings.json` by its byte pattern on the analysed build. A binding may also carry a `string_anchor` (an engine string, the referencing function's RVA and the offset of the signature match inside it). On a build whose PE timestamp matches the analysed one, core resolves by pattern and falls back to the anchor; on any other build it resolves by anchor first: it locates the string in the read-only data sections, finds the RIP-relative instruction in the code section that references it (the first `EXECUTE|READ` section, not a name), maps that site to the function base through the exception directory, then applies the binding's offset and resolve. Anchors marked `durable` resolve to the function base itself and hold across repacks; the rest reproduce the pattern result where the function's internal layout is unchanged. `re/tools/anchorcheck.py` proves every anchor resolves to its signature target on the Steam image.
- **KB addresses and the scan cache.** Each binding in `bindings.json` carries `match`, the RVA where its pattern matches on the analysed build. On that build core compares the pattern with the bytes at that address, or with the bytes under a hook core installed there, and scans the section only when they differ. Every other scan goes through core, which keeps the address of each pattern that a scan found exactly once in `swofty/cache/scan-cache.tsv`, keyed by the exe's PE headers, and checks the pattern at that address before it uses it. The loader scans with SSE2 on the two rarest bytes of the pattern. `SWOFTY_RESOLVE=scan` turns the KB addresses and the cache off.
- **Packed builds.** On a set with `"packed": true` (the EA App build), or an exe whose code section measures encrypted at init, core defers every binding in code that still reads encrypted to the window stage, resolves it there and installs its mixins. Bindings that still read encrypted are retried every second, up to 8 times, then fail closed with a reason. A scan by core code or a plugin of a section that still reads encrypted is refused, and an addon init that met a deferred binding or a refused scan runs again once the code decrypts. Core setups that scan or hook game code without a binding (the asset, database, string, event, overlay and telemetry runtime, the popup and career start hooks, the crash heap-error hook and the UI and item hooks) run once the code section reads decrypted, or fail closed with a reason after the last retry. Core never writes into code that reads encrypted.
- **Saves of absent addons.** The profile save holds one top-level container per game mode, named by the mode's `save_data.name`, and each mode's container holds that mode's careers. At each profile load, core copies every top-level container that no loaded mode claims, such as the careers of a career content addon that is off, into its own memory with the game's bag writer, and at each profile save it writes those containers back into the save after the registered ones. A kept container whose name a registered container also has is left out. `loader.log` lines start with `[saves]`. `SWOFTY_SAVE_SPLICE=0` turns it off.
- **ERS new-lap guard.** The ERS system's `vehicle_newlap` handler (`Game_ErsSystem_HandleVehicleNewLap`) looks up the car by walking every participant's vehicle slot, and a participant without a vehicle has an empty slot. Core skips such a participant, and the handler goes on to the next one as it does for a participant that is not the car. `loader.log` lines start with `[ers]`. `SWOFTY_ERS_GUARD=0` turns it off.
- **ERS mode guard.** Each car's physics step reads the car's ERS mode and loads that mode's deploy table. The game sets the mode when it resets the car's ERS system, and a car whose handling file has no `EnergyRecoverySystem` section can get an ERS system that was never reset, with a mode outside the four the game has. Core runs the system's own reset for such a car the first time its step reads the mode, which sets the mode to Medium and fills the ERS energy, and the step goes on. `loader.log` lines start with `[ers]`. `SWOFTY_ERS_MODE_GUARD=0` turns it off.
- **Front-end tile list guard.** The entrant-list tiles of the front-end menus (the showroom's series tiles) look their list up by label when the menu builds. A label whose list is gone, such as f2_2026 after an import removes the f2_2026 entrant lists, makes the game read past the list array or follow a miss pointer and crash in the menu build. Core sends such a tile down the game's own path for a tile without a list and logs the label once as `[fe] tiles:`. `SWOFTY_FE_TILE_GUARD=0` turns it off.
- **My Team vehicle base guard.** Loading a My Team career reads each saved vehicle base and builds its AI config from the base's vehicle row (`Game_Load_MyTeamVehicleBases` > `Sess_Load_VehicleAiConfig`) without checking that the row exists. A base saved on an addon's vehicle, such as an engine supplier's `myteam_mes_porsche_2026` with that addon off, makes the game read garbage and crash while the save loads. Core skips that base and the rest of the career loads, only for a vehicle row of a known addon (`myteam_mes_` for More Engine Suppliers) that the game database really has no `entrants.vehicles` row for. The row index there reads as missing for vehicles the game loads fine, stock (`myteam_mercedes`) and addon ones alike, so a base whose row is in the database, or any base while the database can't be read, is left to the game's own load. Each skipped vehicle is logged once as `[myteam] save:` with the base and the vehicle row, which names the addon to turn back on, and each stock vehicle left to the game is logged once too. `SWOFTY_MYTEAM_VEHICLE_GUARD=0` turns it off.
- **My Team vehicle heal.** A My Team car is a custom vehicle in the entrants system (kind 1, saved in the profile's entrants `vehicles` list). Launcher 1.9.21 dropped every saved My Team car on load and 1.9.22 the More Engine Suppliers ones, and the next save wrote the profile without them. Such a career then crashed loading its weekend, in the cutscene driver actor (`Game_CutSceneScript_ApplyDriverPartOptions`, F1_25.exe+0x24256e), or entering a session (`Sess_Build_SessionVehicleClassLists`, F1_25.exe+0x2458792). Core rebuilds a missing car with `Ent_EntrantsSystem_ReplaceVehicle` from a stock My Team car, with that stock car as its base car (vehicle +0xcf2, as `Career_MyTeamSetup_CreateTeamAndVehicle` sets it): `myteam_mercedes_2026` or another 2026 My Team car when the career's stock cars are 2026 cars, else `myteam_mercedes` or another 2025 one. A My Team car without a base car keeps Team HQ from loading, so a car without one (1.9.25 rebuilt cars that way) gets the vehicle of its own name as its base when the career loads: the stock My Team car, or for an engine supplier addon's car its own `myteam_mes_` vehicle while the addon is on. When nothing resolves, the log names the entrants system and both vehicle tables with their slot counts. It does so on `career.loaded` for every kind 1 car the career's entrants hold that resolves to nothing, and at the first vehicle lookup of a session entrant (`site_Sess_SessionEnter_VehicleLookup`). The next save keeps the rebuilt car. Each rebuilt car is logged once as `[myteam] heal:` with the stock car it took. When every car resolves it only reads. `SWOFTY_MYTEAM_VEHICLE_HEAL=0` turns it off.
- **My Team vehicle keep.** A saved My Team car whose vehicle row is gone (an engine supplier addon's car with the addon off) used to be skipped by the vehicle base guard: the next save wrote the profile without it, and a new My Team career took its id, so the old career later raced the other career's car. With the keep armed, the guard instead hands the loader the `entrants.vehicles` row of a stock My Team car (`myteam_mercedes_2026` or another 2026 one for a `_2026` car, else `myteam_mercedes` or another 2025 one), so the game stores the car with every saved field. At `site_Game_MyTeamVehicleBases_NextBase` core copies that car into a shadow and makes the live car the stock one (file_name, engine at +0xce9, base car at +0xcf2), so the career loads and its id stays taken. When the profile saves, `site_Game_MyTeamVehicleBases_SaveRecord` in `Game_Save_MyTeamVehicleBases` writes the shadow for a car that is still that placeholder (same address, handle, stock file_name and base car), so the save keeps the original car; with the addon back on its row exists and the real car loads. Each kept car is logged once as `[myteam] keep:`. Both sites are one core mixin set: if either does not install, the guard skips as before. `SWOFTY_MYTEAM_VEHICLE_KEEP=0` turns it off; `SWOFTY_TEST_MYTEAM_KEEP_LABEL=<file_name>` treats that car as one whose row is gone (tests).
- **Standings track guard.** The standings screens (Team HQ > Standings) build one row per round of the season and look each round's track up in the career's track data. A round at a community track that is now off has no track data, and one of the two paths that read it does not check. Core sends such a round down the game's own path for a round without track data, which leaves that round's track empty. `loader.log` lines start with `[career] standings`. `SWOFTY_STANDINGS_GUARD=0` turns it off. The weekend list the R&D table and other Team HQ screens build reads each round's track record the same way; a round whose track has no record, such as Paul Ricard without a Paul Ricard addon, gets the same treatment and is logged once per track as `[career] weekends:`.
- **AI corner start guard.** The AI update (`Ai_Job_UpdateCarsParallel`) takes the next corner start line ahead of each car and reads its per-car entry without a check. A track whose AI line has an incomplete set of corner starts and ends leaves no line ahead for some cars, and the read faults on a null pointer. Core sends such a car down the game's own path for a line without an entry (`site_Ai_UpdateCars_CornerLineLoad`, `site_Ai_UpdateCars_NoCornerLine`), so the car keeps driving its line, and logs the first one. `loader.log` lines start with `[ai] corner start`. `SWOFTY_AI_CORNER_GUARD=0` turns it off.
- **Replay recorder grid guard.** The replay and flashback recorder (`Ne_Replay_WriteFrames`) copies each recordable's serialized state into a state holder sized at registration for a stock grid, with no check against the holder's capacity. A session with more vehicles than the stock 22, such as a career addon that adds rows to the grid, makes some recordables' state larger than its holder; the copy overruns into the next heap block and a later frame faults in `Ne_Replay_WriteFrames+0x752`. Core moves such a recordable to a state holder of the next class that fits, with twice the state's size, at `site_Ne_ReplayAfterRecord`, so every recordable is recorded whole and the session keeps every car. Only a state no class holds (past 0xffff bytes, an allocation that fails, a build whose holder classes differ) is cut to nothing; the recorder then writes an empty state for that recordable, and reading the replay back (flashback, instant replay, highlights) skips its apply in `Ne_ReplayRecordable_ReadFrom` so it keeps its current state instead of reading garbage. `loader.log` lines start with `[replay]`. `SWOFTY_REPLAY_GRID_GUARD=0` turns it off.
- **Team HQ track guard.** The Team HQ screens build a track node for each calendar event (`Career_TeamHqAdvance_BuildTrackNode`) from the career's track data, and read the event's track record and its track without a check. A track with no record, or a career whose mode, season and format match no track data set, such as a Progressive Career saved on an older version, faults as the second Team HQ entry opens. Core sends such an event down the game's own empty node path, so the event shows no track. `loader.log` lines start with `[career] teamhq`, one for each track. `SWOFTY_TEAMHQ_TRACK_GUARD=0` turns it off.
- **Activity resume guard.** Continuing a career reports the career activity to the platform (`Game_ActivitiesUIDeeplinkManager_ReportCareerActivityResume`), which asks a `.data1` body for the race length text of the championship. A career whose current track is not in the game mode's track list, such as Miami in a 2016 Progressive career, logs `UI_TRACK Track [miami] is not found in game mode tracklist` and the body reads a field of a ui variable that does not exist, which faults as Continue loads the save. Core resumes at the body's end with its default text (`full`), so the report goes on without a race length. `loader.log` lines start with `[career] activity resume`. `SWOFTY_ACTIVITY_RESUME_GUARD=0` turns it off. Steam build only: the `.data1` body is encrypted on a packed build.
- **Events sequencer record guard.** Entering a career session runs `Game_CareerEventsSequencer_Initialise`, which adds the team mate asset groups of the session's event by collecting the records of the career event table that match the event's record and reading the first. An event whose record collects no match (a calendar entry whose track is missing, for example from a third-party calendar package) collects nothing and the read faults with ACCESS_VIOLATION reading 0x0 at `Game_CareerEventsSequencer_Initialise+0x1020` as the first session loads. Core resumes at the cleanup that already handles an empty collection, so the session enters without the team mate asset groups. The same block then looks the team mate's driver up in the entrants system and passes the result unchecked to `Game_CareerEventResourceManager_AddDriverMorphData`; a team mate whose driver the entrants system does not have (seen in My Team and Progressive careers) faults reading 0x8 at `Game_CareerEventResourceManager_AddDriverMorphData+0x82` at every load of that career's next session. Core skips that call, so the session enters without the team mate's driver morph assets, and logs the team mate's driver domain and stat id once. The player's own driver goes through the same lookup and call further on, and core skips it the same way when the player's driver is missing. `loader.log` lines start with `[career] events sequencer`. `SWOFTY_SEQUENCER_RECORDS_GUARD=0` turns all three off.
- **Race retirement driver guard.** When a car retires, `Sess_InGameRace_Update` posts a retirement message that names its driver: it finds the car's entrant, looks its driver up in the entrants system and hands the result unchecked to the game's driver name fill. A car whose entrant's driver the entrants system does not have (seen in Progressive careers, as AI cars retire) faults reading 0x1f0 under `Sess_InGameRace_Update+0x77e`. Core writes the name fill's own empty name into the message and skips the call (`site_Sess_InGameRaceRetirementDriver`), so the message shows no driver name and the race goes on. `loader.log` lines start with `[race] retirement`, once per car and driver ref, with the car's vehicle index, its driver's domain and stat id and why the entrants system has no driver for it. `SWOFTY_RACE_RETIREMENT_GUARD=0` turns it off.
- **Wheel tyre instance probe.** The renderer module's per-vehicle job (`Game_GameRendererModule_Slot58`, `0x1401717b0`) calls `Game_Vfx_UpdateWheelTyreInstance` (`0x1445acb00`) once per wheel, which walks an outer list of 0x20-byte items, tests the index against `(end - begin) >> 5` unsigned and, for each index, scans an inner list of entries whose u32 lists may not hold it; every miss captures a stack trace. A trace-only hook on the function's first instruction is armed while a session is entered: from `StateSession` or `StateLoadSession` going to Entering, for 20 s, cut to 10 s after `StateSession` reaches Updating. Outside that window a call is one relaxed atomic load. Inside it the hook reads, with guarded reads, the gate its prologue takes and both lists, and logs each distinct value once, through a lock-free dedupe; the 8th value disarms it until the next session entry: `[session-job] 0x1445acb00 entry, session N: vehicle V, wheel W; the nested loop runs; outer list <begin>..<end> (<bytes>, <items>, <verdict>, loop count <n>); inner list ...`. A negative, huge or ragged size adds a `[session-job] [warning]` line. Each logged value is also a black-box note. `SWOFTY_SESSION_JOB_PROBE=0` turns it off.
- **Load-stall report order.** A load-stall report (`swofty\stall-<time>.txt` and `[stall]` lines) lists the threads whose top frames are not in a wait first (`== Threads not in a wait`), those with a frame in `F1_25.exe` ahead of the rest, each with the registers it was suspended with, the non-volatile registers the unwind restored at its first game frame, the first 24 qwords of that frame's stack and its top 16 frames. The thread table follows unchanged.
- **Setup screen car guard.** The car setup screen refreshes its differential ranges by asking whether its car is handling version 100, and four of its handlers read the car without testing it. A refresh that runs after the screen has lost its car faults reading the car; core skips the range update through the game's own path for a car that is not version 100 and logs `[setups] the setup screen has no car yet; skipped` once. `SWOFTY_SETUP_VM_GUARD=0` turns it off.
- **Placed record bound.** Each of the game's three upload heaps keeps 128 records of the placed buffers made in a frame (`Render_Gfx2Heap_BumpAllocPlacedResource`), and the writer takes the next index with no bound; the 129th record would land on the heap's command list counters and pointers. Core counts the records per heap and logs the high-water mark every 15 s and each new maximum past 64 (`[gfx] placed records`), and puts the high-water mark in the crash report's Game state section. With an index past 127 it skips the record, puts the count back to 128 and releases the resource five seconds later. `SWOFTY_PLACED_RECORD_GUARD=0` turns the skip off; the counting stays on.
- **Teammate pairs guard.** Session enter pairs the first two cars of every team for strategy (`Sess_Strategy_UpdateTeammatePairs`) and sorts the team's car records first; the sort throws when a record is not live, which a third car's record is, and the game ends with a fast-fail (`FAST_FAIL_INVALID_ARG`) as the session loads. Core limits the pairing to the first two cars of a team (`site_Sess_Strategy_TeammatePairSort`), so the third car stays unpaired and still races. `loader.log` lines start with `[strategy]`, one for each team with more than two cars per session, with its team and car count. `SWOFTY_TEAMMATE_PAIRS_GUARD=0` turns it off.
- **Tyre slot guard.** Each car's tyre component keeps a table of the tyre options its own compound class has at the session's track, and the game refits a car by looking its fitted set's option up there, falling back to Medium (or Wet for a wet set) without a check. A car whose class has neither, such as an F2-layout class at a track whose F1 compounds it lacks, faults on session enter. Core gives such a set a slot with the compounds of another slot of the car's own class (dry first for a dry set), and skips the refit when the class has no usable slot. `loader.log` lines start with `[tyres] slot guard`. `SWOFTY_TYRE_SLOT_GUARD=0` turns it off.
- **Garage crew guard.** The session's garage crew spawn (`Game_GarageCrewModule_SpawnGarageCrew`) creates one crew instance for each assignment record of a garage and stores them in a two-entry array with no bound, and the array's neighbour is the pointer to the list it iterates. A team that fields a third car puts a third record in its garage, and the spawn overwrites that pointer: the heap error `Invalid address for this heap` as the session loads. Core keeps the first two records of a garage whose slot is below 2 and drops the others from the spawn's list (`site_Game_GarageCrew_SpawnVector`), so the third car still races and has no garage crew. `loader.log` lines start with `[garage]`, one for each dropped car, with its team, number and driver. `SWOFTY_GARAGE_CREW_GUARD=0` turns it off.
- **Pit slot guard.** The AI pit decision (`Sess_PitStrategy_EvaluateAgainstPitList` and `Sess_PitStrategy_EvaluateByRank`) compares the car's race position with that of every car in the global pit list, reading each car's slot from the session's race position table with no check that the slot exists. The list is never pruned, so it can name a vehicle whose slot is gone, and the read faults on a null pointer (Classic Career 2012, vehicle 21 with slots 0-20 and 22 filled). Core skips a listed car without a slot, and answers no for a car without a slot of its own (`site_Sess_PitEvalOwnSlot`, `site_Sess_PitEvalListSlot`, `site_Sess_PitRankOwnSlot`, `site_Sess_PitRankListSlot`). `loader.log` lines start with `[pit]`, one for each vehicle. `SWOFTY_PIT_SLOT_GUARD=0` turns it off.
- **Pit box guard.** `Game_PitLane_ProjectBoxPose` keeps a car in its garage aligned to its pit box and reads the box's cached spline handle from a 40-slot array with no bound on the box number. A third car in a garage (Classic Career seats more than two cars to a team) has box -1 and the read faults. Core sends a box of 40 or more to the function's failure return, so the car is left where it is (`site_Game_PitLane_BoxSlotRead`, `site_Game_PitLane_BoxPoseFalse`). `loader.log` lines start with `[pit]`. `SWOFTY_PIT_BOX_GUARD=0` turns it off.
- **Garage setup guard.** The garage's setup list rebuild (`FUN_140c22ad0`, `Game_GarageSetups_FindOwnerName`) looks up the owner name of each saved setup in a hash set of the current grid's entries with no end test, so a setup saved for an owner that is no longer in the set walks onto the set's end marker and faults reading `[entry + 0x38]` at `F1_25.exe+0xc22c47` ("reading 0xffffffffffffffff"). At `site_Game_GarageSetups_EntryStep` core checks that the entry reads down to its id and otherwise continues at `site_Game_GarageSetups_NotFound`, the function's own not-found exit, so the row gets an empty owner name. `loader.log` lines start with `[garage]`. `SWOFTY_GARAGE_SETUP_GUARD=0` turns it off.
- **Session enter guard.** `Sess_Ai_BuildVehicleRecords` (`F1_25.exe+0x38a0e00`, called from `Game_GameModule_OnSessionEnter`) builds an AI record for each vehicle slot from the first asset group that lists the car's name hash, and reads that group's node with no check that one was found. A car that no group lists, such as Supercars cars or an era box on a community track without AI asset groups for them, leaves the node vector null and the session start faults reading `0x0` at `F1_25.exe+0x38a41bc`. Other code reads the records by vehicle slot, so a vehicle cannot be skipped. At `site_Sess_AiRecords_NameHash`, right after the hash is computed, core looks the hash up in group 0's map and, when it is missing, replaces it with the key of the map's leftmost entry, so the game's own code builds a full record and the car borrows another car's AI entry. `loader.log` lines start with `[session]`, one for each of the first four cars. `SWOFTY_SESSION_ENTER_GUARD=0` turns it off.
- **AI line set guard.** `Sess_Build_AiSystem` (`F1_25.exe+0x5ff750`) stores six per-car pointers in each AI record (the racing line cache and five lookup tables) from hash maps keyed by the car's name, and stores 0 for a name no map lists; `Ai_Job_UpdateCarsParallel` dereferences them for every car (`Ai_LineCache_UpdateIfChanged+0x5e`, reading 0x178). A third car in a team is such a car. At `site_Ai_BuildSystem_RecordPushed` the guard copies the first record's pointer into each null pointer of the record just pushed. It arms only when the generated headers export the site. `SWOFTY_AI_LINE_SET_GUARD=0` turns it off.
- **Garage slot guard.** `Sess_Assign_GarageSlotsByPreference` reads a team's garage from the track world's garage vector at the team's position in the team order, and `Sess_Assign_GarageSlotsByTeamOrder` never compares that position with the garage count on its listed-team path. A box with more teams than the world has garages (F1 2010's 12 teams at a 10 garage community track) reads past the vector and faults in `Sess_Set_GarageSlotEntrant`. Core sends a team past the garage count to the function's own return (`site_Sess_GarageSlots_GarageLoad`, `site_Sess_GarageSlots_Done`), so the team gets no garage slot and its cars still race. `loader.log` lines start with `[garage] slots`. `SWOFTY_GARAGE_SLOT_GUARD=0` turns it off.
- **Theatre list guard.** Theatre's two lists of saved replays and highlights ask the list object for each saved item's save slot (`Game_TheatreList_FindItemSaveSlot` for the recent list, `Game_TheatreList_FindItemSaveSlot_Alt` for the saved list), which looks the item's owner up in a hash set of the current list's entries with the same end-test-less walk as the garage setups, so an item recorded with a car or team the list no longer has walks onto the set's end marker and faults reading `[entry + 0x38]` at `F1_25.exe+0x2bfc6a7` ("reading 0xffffffffffffffff", 0.4 s after `theatre_container` opens). At `site_Game_TheatreList_EntryStep` and `site_Game_TheatreList_EntryStepAlt` core checks that the entry reads down to its id and otherwise answers with no slot record at the function's own epilogue (`site_Game_TheatreList_NoSlot`, `site_Game_TheatreList_NoSlotAlt`), so the item gets no row. The list builder passes each record's index as its row index too, and the row getter (`Game_TheatreRows_GetRow`) appends only one row before it reads the row at that index, so the item after one without a row read its row past the row array (`F1_25.exe+0x1f0ba29`, "reading 0x41200026"). At `site_Game_TheatreRows_RowOffset` core points an index past the rows at the row the getter just appended; the row keeps the record's index as its `slot_id`, which Theatre reads back to act on the selected item. `loader.log` lines start with `[theatre]`. `SWOFTY_THEATRE_LIST_GUARD=0` turns all of it off.
- **Tile list select guard.** A list widget whose selection is bound to a view-model property walks its children for the one whose data-context component carries the new selection (`Game_TileList_ApplyBoundSelection`), reading each child's component array at `[child + 0x30]` with no null test. Choose Driver's tile list sets its selection on the F2 drivers tab after it respawns its tiles (`children_triggered`), and a tile with no component array there faults reading 0 at `F1_25.exe+0x3838fe8`. At `site_Game_TileListSelect_ChildStep` core checks that the child, its component array and its first component read, and otherwise continues at `site_Game_TileListSelect_ChildNext`, the walk's own step to the next child, so that tile never takes the selection and the screen keeps working. `loader.log` lines start with `[tile-list]`. `SWOFTY_TILE_LIST_SELECT_GUARD=0` turns it off.
- **Chassis registry guard.** `Car_Chassis_Build` registers each car's physics body in a 26-slot registry with no bound, so the 27th car (26 cars plus the safety car) writes over the next heap block header. Core sets the registry pointer to zero at `site_Car_ChassisRegistryCount` once the count reaches 26, which makes the game's own branch skip that registration. `loader.log` lines start with `[car]`. `SWOFTY_CHASSIS_REGISTRY_GUARD=0` turns it off.
- **Track acclimatisation guard.** The Track Acclimatisation practice programme takes its targets from the track's acclimatisation data, and a track without that data, such as an imported community track, leaves the programme with none. Two of the programme's slots read the current target without checking that one exists: the refresh (`Game_PracticeTrackAcclimatisation_RefreshState`), which runs for every practice programme as the car leaves the garage, and the penalty flag (`Game_PracticeTrackAcclimatisation_FlagCurrentTarget`), which runs when the car gets a penalty or warning. Core returns from both when the programme has no targets, as the programme's start does. `loader.log` lines start with `[acclim]`. `SWOFTY_ACCLIM_GUARD=0` turns both off.
- **Time Trial leaderboard guard.** View Leaderboards in Time Trial (`Game_TimeTrialLeaderboard_SelectBoard`) searches the reader's board list for the board named after the track and weather, and reads that board's thresholds without a null check. With no board for the key, such as with the online services off, core sets the function's result to false and continues at its own cleanup, so the screen does not open the board and the game stays up. `loader.log` lines start with `[leaderboard]`. `SWOFTY_LEADERBOARD_GUARD=0` turns it off.
- **Thrustmaster LCD guard.** With a Thrustmaster wheel connected, `Game_ThrustmasterLcd_UpdateSectors` looks up each sector entrant's record and reads its team name without a null check, and a box with 24 entrants on a 22-car grid returns no record for the extra cars. Core continues at the function's own not-found path when the record is null, so the wheel keeps its last team name and the game stays up. `loader.log` lines start with `[tmlcd]`. `SWOFTY_TMLCD_GUARD=0` turns it off.
- **Estimate lap time guard.** The virtual session's lap estimate (`Sess_VirtualSession_EstimateLapTime`, used by the red flag unlap simulation, the qualifying pace debug and the race finish) passes a vehicle's tyre object to the compound query with no null check, and a car that has just been retired from the player's race (a Terminal Damage or pause menu retire) has none: ACCESS_VIOLATION reading 0x10 at `F1_25.exe+0x2e80ce0`. Core continues at the function's own return when the object is null, so the lap time passed in comes back unchanged. It arms only when the generated headers export `site_Sess_VirtualSession_EstimateTyreQuery` and `site_Sess_VirtualSession_EstimateTail`. `loader.log` lines start with `[session] a virtual session lap estimate`. `SWOFTY_ESTIMATE_LAPTIME_GUARD=0` turns it off.
- **Grand Prix continue F1 World car guard.** Continue on a Grand Prix save (`Game_GrandPrixContinueVm_PressEntry`) runs two offline checks that compare the save's setup mode category with the category of the player's F1 World car, and show "ONLINE CONNECTION REQUIRED: You must be online to resume this saved Grand Prix" (`f1w_car_offline`) or `continue_solo_gp_f1w_offline_warning` when they match. On profiles where the F1 World car holds the real F1 category, every F1 season save matches, and the launcher always runs offline. When the categories match, core compares the F1 World car's category with the `f1_world` setup mode's; unless they are the same, the game's own check takes its no-match path, so the save loads. A save on the F1 World car still gets the popup. `loader.log` lines start with `[gp] continue:`, one per press. `SWOFTY_GP_F1W_CHECK_GUARD=0` turns it off.
- **Grand Prix weekend track guard.** Entering Grand Prix begins the mode's current weekend, and `Game_TyreAllocationComponent_SetPresetChoice` indexes the career's track data records by the weekend's track stat id and calls `Ne_FatalAbort` when the stat id has no record. A Grand Prix remembers the track it last raced, so one last raced on an added track whose addon is now off or gone aborts the game at every entry into Grand Prix. When the weekend's track has no record, core puts the stat id of the melbourne record (else the first record) into the Grand Prix weekend before the read, so the game reads a track it has. Another mode's missing track is logged and left to the game. `loader.log` lines start with `[gp] the grand_prix weekend races track stat id`. `SWOFTY_GP_WEEKEND_TRACK_GUARD=0` turns it off.
- **Career calendar track list guard.** A career's schedule component saves its calendar as `custom_track_list`, one byte (the event's id) per entry. `Career_ScheduleComponent_Load` pushes every event row of the career's event list whose id matches each stored byte, and addon seasons and tracks add events that share ids: the calendar multiplies on every save and load until a save fills `SAVE_PROPERTY_BAG_TEMP` (Ne_TempPool_ReportError < Ne_TempPool_Alloc < Ne_SaveObject_ReserveChildSlot from `F1_25.exe+0x1272188`). Core loads exactly one event per stored entry (`site_Career_ScheduleComponent_TrackListPush`, other matches continue at `site_Career_ScheduleComponent_TrackListNextRow`): the first row with that id not yet in the calendar, or the first match again when all are, which keeps a track that runs twice in one season. A stored list longer than the season is a list the game already blew up: each run of one id reads as one entry and entries past the season's length are dropped. The season's length is the larger of the component's event list length (+0x2c8, the full default list's length) and the race weekends on the career's own calendar (the RaceWeekend activities of the busiest driver calendar in the component's current season record, loaded from the same save), or 64 when neither is set, so a season that races more weekends than the default list (a long addon or custom calendar) keeps every round. `loader.log` gets one `[saves] custom_track_list loaded` line per load (stored entries, calendar events, season length, race weekends, skipped matches, repeated events, dropped entries) and a `[saves] custom_track_list saved` line when a save's count changes. `SWOFTY_TRACK_LIST_GUARD=0` turns the guard off; the count lines stay.
- **Audio job queue fix.** Wwise asks the game for audio job workers through `Snd_Request_JobWorker`. The game hands each request to an idle one of its 12 audio worker threads or queues it in the first free of 24 slots, and the workers take queued requests from slots 0-11 only. A request queued in slots 12-23 never runs: the workers spin, the Wwise audio thread waits for that job holding the Wwise lock, and the game's watchdog ends the game 30 s later. Core passes Wwise a thunk in place of each worker function. After each request a thunk runs, and after each `Snd_Request_JobWorker` call, core moves the requests queued in slots 12-23 into free slots 0-11 under the queue's lock. `loader.log` lines start with `[audio]`. `SWOFTY_AUDIO_QUEUE_FIX=0` turns it off.
- **Runtime assets.** Core reads `swofty/assets.json` and changes game content in memory, with nothing written into the game folder. Without the file it does nothing.

| Feature | Key in `swofty/assets.json` | Status | Core part |
|---|---|---|---|
| `group` | `asset_groups`, `asset_groups_auto` | stable | `assets.cpp`: entries added to the asset manifest after it is parsed |
| `erp` | `resource_erps`, `resources`, `resources_trace` | stable | `resources.cpp`: overlay archives the launcher built (`resource_erps`) or the core builds in `swofty/cache/` (`resources`), read first by every group that lists a target archive |
| `db` | `db_edits`, `early_stage` | stable | `gamedb.cpp`: edits applied when the game database loads |
| `lang` | `lang.<code>.strings`, `lang.<code>.table`, `lang.<code>.priority` | stable | `overlay.cpp`: string tables added after the stock table |
| `file` | `overlay`, `lang.<code>.replace` | experimental | `overlay.cpp`: files under `swofty/overlay/` served in place of game paths |

An experimental feature applies only when `"features"` in `swofty/assets.json` lists it. `"early_stage": true` makes the loader load addons inside the game's `CreateMutexW("Codemasters F1 25")` call, before the game database loads, and core runs its window-stage handlers at the window trigger. `SWOFTY_EARLY_STAGE=1` or `0` overrides it. File paths in `swofty/assets.json` are relative to `swofty/`.

## Game log

`swofty_gamelog.dll` logs warnings and errors from every channel, and info from the UI and flow channels, by default. Configure it with `"game_log": { "level", "channels", "rate", "repeat", "max_lines" }` in `swofty/session.json`, or with the `SWOFTY_GAME_LOG`, `SWOFTY_GAME_LOG_CHANNELS`, `SWOFTY_GAME_LOG_RATE`, `SWOFTY_GAME_LOG_REPEAT` and `SWOFTY_GAME_LOG_MAX` environment variables, which take precedence.

## Build

```sh
native/build.sh
```

Runs `re/tools/bindgen.py`, then cross-compiles the three DLLs with zig for `x86_64-windows-gnu` into `native/build/` and copies them to `native/dist/` with `features.json`. safetyhook, Zydis, zstd 1.5.7 and stb_image 2.30 are vendored in `third_party/` with their licences, and `third_party/titillium-web/` holds the SIL OFL licence of the overlay font. `tools/hud_font_sdf.py` regenerates the overlay font atlas (`src/core/hud_font_data.hpp`, `src/core/hud_font_atlas.hpp`) from Titillium Web SemiBold at a pinned google/fonts commit. safetyhook carries one local change, marked `Swofty:` in `trap_threads`: it keeps an ntdll page executable while it patches it. The build is deterministic.

The launcher takes the files from `loader/` beside its `bin/` folder in a release, from `native/dist/` in a checkout, or from the folder named by `SWOFTY_LOADER_DIR`.

## Loading under Proton

Wine uses its builtin `version.dll` unless the prefix overrides it for the game. The launcher writes `[Software\Wine\AppDefaults\F1_25.exe\DllOverrides] "version"="native,builtin"` into the prefix's `user.reg` for the session and journals it. A Steam session also passes `WINEDLLOVERRIDES=version=n,b` to the game, unless `WINEDLLOVERRIDES` already names `version`, and logs whether the prefix has the override. Windows needs no override.

## Wine check

```sh
native/test/run_wine_test.sh
```

Builds a small stand-in `F1_25.exe` that carries the signatures and the real home-menu instructions, the test plugins and test bindings, then runs it under Wine with `native/dist/` in each mode. It checks the proxy, the load trigger, loading from `swofty/addons/` and the legacy `swofty/mods/`, both init exports, the ADDON SETTINGS tile, mixin chains, refused and conflicting registrations, the settings bridge with and without a requests path and with the old settings fields, the ownership check for `owned_items`, the ERS new-lap guard on a byte-for-byte copy of the game's handler, the ERS mode guard on a byte-for-byte copy of the game's ERS mode load, with and without the guard, the standings track guard on a byte-for-byte copy of the game's standings track read, with and without the guard, the Time Trial leaderboard guard on a byte-for-byte copy of the board search, the track acclimatisation guards on byte-for-byte copies of the game's refresh and penalty flag, which fault as the game does with the guard off, `session.json`, the game log, and the crash log and reports: an access violation, a non-zero `ExitProcess`, a fatal Ne heap error (a block overrun into its neighbour, freed) and `Ne_FatalAbort` each write a `crash-<time>.txt` that parses into its sections, with the faulting heap block and its corrupt neighbour, and a real minidump beside it. With an injected hook that serves int3 breakpoints in `GetModuleFileNameW` the report is still whole, and with that breakpoint left unowned on the writer only the header is cut short. With a hook target on the ntdll page of `NtProtectVirtualMemory` the crash init still finishes. A staged run loads one plugin at the early stage and two at the window stage, and checks that a window-stage binding still resolves on a function the early plugin already hooked, and that wrong or ambiguous patterns are still refused, that bindings resolve at their KB address without a scan, and that one whose KB address holds other bytes is scanned. A packed run encrypts the code section of a second stand-in exe in the file and decrypts it before the window, as the EA App build does. It checks that nothing in that code is resolved, scanned or hooked at the early stage, that bindings, mixins and the core's own setups follow at the window pass with one `[bind]` line per binding and a summary, and that the hooks then run. A run whose code never decrypts checks that everything fails closed with a reason after the last retry and that the code is never written. A plain run of the same exe with a set that is not packed checks that everything still resolves at init. Across the modes it checks that the scan cache is written on the first run, used on the next, rewritten when an address is stale or the exe differs, and off with `SWOFTY_RESOLVE=scan`. CI runs it on every push.

```sh

```
